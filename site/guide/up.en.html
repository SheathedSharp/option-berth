up starts what the manifest declares, in dependency order. --wait returns only when the selected services actually listen and pass their health checks.

Start in dependency order

Services start in the order given by depends_on. A service with prepare: runs that prerequisite first, in the same working directory, and starts its long-running cmd: only if the prerequisite succeeds. Services that are already running are skipped, and each service keeps its own log file and run record.

What --wait proves

Without --wait, up has started processes; it has not shown that they are usable. With --wait, a service with a port must listen, a service that declares health: must also pass that check, and a portless worker is ready when its run record becomes active. Services that were already running are included in the wait.

  • Each service waits within its own ready_timeout:, 30s by default. --wait-timeout is an overall ceiling, and it can only tighten the per-service budgets, never loosen them.
  • prepare: does not count against the readiness budget. A slow install needs prepare_inputs: caching, or a larger script timeout on the caller's side.
  • Without waiting, a started service carries ready: false, and the table says readiness was not confirmed. That is not a failure.
  • A service that times out is failed with reason ready_timeout, and the message says whether the service's own budget or the caller's ceiling expired first.

When a start fails

Each entry in services[] is started, skipped or failed. A failure carries a branchable reason and a hint that points at evidence which really exists. A partial success is still exactly one JSON value, with exit code 1.

Restart without losing the address

restart stops the project and starts it again. With --only it restarts just the named services and leaves the rest running, and it keeps the worktree's port: auto reservation, so a service gets its original address back. restart does not wait for readiness; use up --wait when the caller needs proof.

Boundaries

  • Service working directories must be under $HOME by default. --allow-outside-home is an explicit decision, not a silent fallback.
  • machine: dependencies are observed, and up never starts or stops them.
  • workspace: references supply addresses only. up never starts another checkout's service, and never establishes depends_on across checkouts.
  • up writes no manifest and no Git state. A person adopts a manifest before up reads it here.
