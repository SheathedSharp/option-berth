Every command in this guide reads or writes the same chain: worktree → manifest → service → run → runtime facts. Each station has exactly one writer, and the next station reads only what the previous one published. There is no second source of state.

Five stations

What each station publishes and what the next one reads
StationWho writes itWhat it publishes
WorktreeGit, observed by the engineThe checkout root path and the wt_… identity a run belongs to.
ManifestA personoberth.yaml: services, ports, dependencies, health checks, references.
ServiceThe engine, at startWhich declaration it started, in which order and on which address.
RunThe engine's run registryThe pid, start, end, exit code and log path of one process.
Runtime factsThis round's observationsAlive, listening, healthy, and the reason an earlier run ended.

Why the order matters

A single “is it up?” flag would flatten the chain, and every reader would have to work out the rest for itself. So each step is published before the next one is allowed to decide anything: attribution before lifecycle, lifecycle before observation, observation before readiness.

That is why up --wait can return a real answer, and why status can report a running service with an unknown port without contradicting itself.

A run belongs to the checkout that started it

Attribution combines three inputs: this round's path observation, the manifest's content index and the run identity. Two worktrees of the same repository therefore never share services, a port, a database name or a stop.

Ports follow the same rule. port: auto is reserved per run and handed back on stop, so the second checkout asking for “the API port” gets its own answer instead of a collision.

An unread fact stays unknown

Failure, cancellation and an incomplete scan may not become “free”, “gone” or “healthy”. A port missing from the listener table means the fact was not observed. It never means the port is free. A successful signal means the signal was delivered, not that the process exited.

An unread fact is written as unknown, and unknown is not success. status shows this rule in action, and Where the product stops turns it into a product boundary.

Where each station is taught

  • Declare what should run covers the manifest, and the one thing a model may not do to it.
  • up covers dependency order, automatic ports, and what readiness really proves.
  • Several worktrees at once covers attribution, data paths and leftover checkouts.
  • logs covers the run's own output, without rebuilding a shell pipeline.
  • status covers the four runtime facts, and the honest “I cannot see”.
