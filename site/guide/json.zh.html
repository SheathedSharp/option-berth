每条命令都只有一种机器形状：stdout 恰好一个 JSON 值，诊断写 stderr，错误码稳定。同一条命令同时回答人和 agent，只是读者不同。

规则

  • 带普通 --json 时，stdout 恰好一个 JSON 值。诊断写 stderr，绝不混进来。
  • 流式命令用 NDJSON，一行一个值。
  • 退出码：0 成功，1 运行失败，2 参数或选项错误，130 被 Ctrl-C 中断。
  • 错误形状是 {"error":{"code":"…","message":"…","hint":"…"}}。hint 指向真实存在的证据。
  • 没有字段会被接受却不被读取。发布出去的字段是每个客户端都可以依赖的承诺，所以协议构建会在没有处理器的字段上失败。

一次完整读取

部分成功也仍然是一个值。下面这次 up --json 起了一个服务、失败了另一个；退出码是 1，两个结果都在同一个文档里。

state
started、skipped 或 failed：启动动作的结果，不是就绪声明。
reason
稳定、可分支的失败原因，例如 start_failed、port_occupied 或 ready_timeout。
hint
确定性的下一步，只指向真实存在的证据。进程真起来了才指向服务日志，依赖没就绪就指向依赖日志；没有可执行的下一步时留空。
port_holder
在 port_occupied 时出现：占用者的端口、pid、命令和类型；如果占用者是我们的服务，还带组名、服务名和 run id。
ready
CLI 的注解，不是 daemon 事实。--wait 确认就绪后为 true，没有等待时为 false。false 不是失败。

字段缺席不代表什么

缺席不是 0，也不是 false。没有 observation 说明监听表可用；没有 running_services 说明“没有观察”，不是 0。观察错误码不表示“没有东西在监听”，未知也不是成功。事实读不到时，文档会说出来，而不是用默认值填上缺口。
