A failure has a log, an exit code and a reason. logs reads the service's own output and the run it belongs to, instead of reassembling a shell one-liner.

One read or a stream

Ask by service name; the port form still works. --once reads once and exits; without it, logs prints the latest lines and keeps following. --lines N bounds a read, and follow mode writes NDJSON, one value per line.

  • A service with a listener reads that process's log; a portless worker reads its run's service log file.
  • The log file is appended across runs. --run current reads only the part of the current run, starting at its recorded offset.
  • --json --once returns one document: source, lines, truncated, service, run_id, pid and status.

The failure you actually need

--run current --first-error reads the current run and locates the first matching line from a fixed vocabulary: error, exception, fatal, panic, traceback, case-insensitive. It returns the line number and the original text. It is a position, not a root-cause judgment; when nothing matches, the JSON says no_first_error.

The document adds log_offset, an optional run_start_unknown, and first_error with line and text, or no_first_error. If the log rotated past the recorded offset, the read falls back to the start of the file and sets run_start_unknown, so you know the lines may include earlier runs.

A portless worker still has a log

A worker with no listener is not a service without output. oberth logs worker --once reads that run's service log file; the run record supplies the status and the offset.

What it will not do

  • It does not read another checkout's service. The name resolves in this worktree's manifest.
  • --first-error finds a position; it does not decide the cause, and it does not hide the lines around it.
  • It does not invent a start. A run record without an offset returns not_found with a suggestion to restart the service once; --run also needs the daemon.
