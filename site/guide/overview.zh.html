oberth 为每个 Git worktree 保留同一份答案：该跑什么、是不是真的在跑、没跑的时候为什么。人读一张表，coding agent 读同一条命令的 --json。这本指南讲这份答案从哪里来。

四个 checkout，四次猜测

worktree 解决的是并行写代码，不是并行跑服务。同一个仓库的四份 checkout 共用一段端口范围、一个数据库名和一份 shell 历史，于是每个会话都要把这同样的三件事重新推一遍，而且每次推出来的结果都略有出入。

oberth 把这些事实按固定顺序写一次，每个读者读到的都是同一份：worktree → 清单 → 服务 → 运行 → 运行事实。后面的环节不会去猜前面的环节已经记下的东西。

一条链，五个站点

事实链的五个站点
站点它解决什么问题它不许做什么
worktree一次运行属于哪个 checkout？属于它不是在其中启动的那个 checkout。
清单该跑什么、在哪个端口、依赖谁？从运行中的进程去猜，或被模型采纳。
服务哪条声明先启动、落在哪个地址上？在依赖就绪之前启动依赖它的服务。
运行pid、开始、结束、退出码、日志路径。因为进程存在就算作在监听。
运行事实活着、在监听、健康，以及为什么结束。把读不到的表写成“没在运行”。

一条事实链按顺序走完这五个站点，每站一节。

这本指南怎么读

  • 第一次来。先安装 oberth，再跟第一个 worktree走一遍：一个示例项目、五条命令，从一个空 checkout 到一个干净的停止。
  • 你已经在跑本地服务。读一条事实链和同时跑多个 worktree，命令章节按需查。
  • 你在接入 agent。从JSON 里的运行事实开始，再看接入 agent的三个调用时机。

两个读者，一个接口

CLI 是唯一的接口。没有第二套 API，没有 MCP server，引擎里也没有模型；--json 是同一份契约换一个程序能读的形状。

llms.txt 为机器列出这本指南，llms-full.txt 收录全部章节的纯文本。

这本指南不是什么

不是契约。确切的 CLI 面、JSON 字段与清单规则在 docs/cli.md；这本指南讲链，细节去那里查。不是产品官网。官网展示产品本身。不是框架教程。示例用 Hello Worktree，因为它只依赖 Python 3；同一条链适用于任何技术栈。
