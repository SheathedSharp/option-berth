A worktree keeps work records: the commands the engine ran, the rounds handed to an agent, and how each of them ended. It is what the next session reads to take over.

The record

One worktree can hold several workplaces, and each keeps its entries in order. A workplace is a named stream of work; the current one receives new entries, and list marks it with ●.

Selectors match in order: exact name, full id, id prefix, name prefix. When several match, the command returns ambiguous rather than picking one. --worktree defaults to the current directory and resolves to the checkout root, so different spellings of one checkout reach the same record.

What gets recorded

  • oberth start writes the run into the current workplace. The Runtime Service closes a detached run when it records that run's exit.
  • oberth agent stream writes one entry per round: turn.started opens it, and turn.completed closes it with the outcome the provider reported.
  • oberth workplace record writes what the engine cannot see: an agent's own attempts, the client's interactive shell, a native agent. Reporting the same --id again updates the entry, so the start and the end of one piece of work may arrive in either order.

How an entry ends

An entry is running, completed, failed or interrupted. An entry whose end was never observed stays running and is never treated as a success. A run stopped by oberth or by the user is interrupted, whatever signal exit code it left behind. Each workplace keeps at most 500 entries and drops the oldest beyond that.

It is not runtime truth

  • status never reads it to decide whether a service is running.
  • show reads back what happened; it does not call the processes of that time back.
  • Without a Runtime Service, reads still open the ledger read-only, and writes need the Runtime Service. up and down write no work record, because a declared lifecycle is not a temporary work entry.
  • A record is evidence of work, not a session restore. It never presents an unobserved ending as a success.
