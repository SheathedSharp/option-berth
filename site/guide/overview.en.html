oberth keeps one answer per Git worktree: what should run, whether it really is running, and why not when it is not. A person reads a table; a coding agent reads the same command with --json. This guide shows how that answer is built, and where it can fail.

Four checkouts, four guesses

Git worktrees solved parallel code, not parallel runtime. Four checkouts of one repository share a port range, a database name and a shell history, so every session works out the same three facts again, and works them out slightly differently.

oberth writes those facts once, in a fixed order, and every reader reads the same copy: worktree → manifest → service → run → runtime facts. A later step does not guess at what an earlier step already recorded.

One chain, five stations

The five stations of the chain of facts
StationThe question it settlesWhat it may not do
WorktreeWhich checkout does a run belong to?Belong to a checkout it did not start in.
ManifestWhat should run, on which port, after what?Be guessed from a running process, or adopted by a model.
ServiceWhich declaration starts, in which order, on which address?Start a dependent service before its dependency is ready.
Runpid, start, end, exit code, log path.Count as listening because the process exists.
Runtime factsAlive, listening, healthy, and why it ended.Turn a table it could not read into “not running”.

One chain of facts walks the five stations in order, one section each.

How to read this guide

  • First time here. Install oberth, then follow Your first worktree: one example project, five commands, from an empty checkout to a clean stop.
  • You already run a local stack. Read One chain of facts and Several worktrees at once, then use the command chapters as you need them.
  • You are wiring an agent. Start with Facts as JSON, then read Coding agents for the three moments to call oberth.

Two readers, one interface

The CLI is the only interface. There is no second API, no MCP server and no model inside the engine; --json is the same contract in a shape a program can read.

llms.txt lists this guide for machines, and llms-full.txt carries every chapter as plain text.

What this guide is not

Not the contract. The exact CLI surface, JSON fields and manifest rules live in docs/cli.md. This guide explains the chain and points there for detail. Not the product site. The homepage shows the product itself. Not a framework tutorial. The examples use Hello Worktree because it needs nothing but Python 3. The same chain applies to any stack.
