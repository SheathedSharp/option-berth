Why this book exists

Worktrees solved parallel code, not parallel runtime. Four checkouts, four guesses. One chain of facts replaces them.

One chain, five stations

Each station is written by exactly one actor. The next station reads only what the previous one published — never a second source of state.

Worktree

Code observes the path and Git identity: repository, branch, dirty count. Everything else hangs from this root, and a run never belongs to a checkout it did not start in.

Read the chapter

oberth status --json

{ "worktree": {
  "root": "/work/hello-worktree",
  "identity": "wt_0123456789ab"
} }

Manifest

A person writes oberth.yaml; an agent may draft it, and only a person adopts it. The manifest declares services, ports, dependencies and health checks — nothing is guessed from a running process.

Read the chapter

oberth.yaml · hello-worktree

name: hello-worktree
services:
  - name: api
    cmd: python3 -u api.py
    port: auto
    health: /health
  - name: worker
    cmd: python3 -u worker.py
    depends_on: [api]

Service

One declaration says what to run, on which port, after which dependency and how to check it. port: auto gives every checkout its own address instead of a shared guess.

Read the chapter

oberth up --wait

api      started   :21730   ready
worker   started   no port

Run

The background process records one run: pid, start and end, exit code and log path. A portless worker is still a run — it simply has no listener.

Read the chapter

oberth logs worker --once

worker: API health=200
worker: API health=200
worker: API health=200

Runtime facts

Code observes what is true now: alive, listening, healthy, and the last exit reason. These are four separate facts; one does not imply another, and an unreadable table is never written as “not running”.

A person reads the table; an agent reads the same command with --json. One interface, two readers.

The book

The core loop is four commands. The rest of the book widens it: declaration, parallel worktrees, handoff, JSON, boundaries.

Two readers, one interface

If you are a person

Install once, confirm the manifest once, then read the table. The same commands serve the whole loop.

oberth status
oberth up --wait
oberth logs api --once
Start with installation

If you are a coding agent

Open with --brief, start with --wait, and read the failure from the current run. Every read is one JSON value on stdout.

oberth status --json --brief
oberth up --wait --json
oberth logs api --once --json --run current --first-error
Read facts as JSON

Both readers use the same command. There is no second interface, no MCP server and no model in the core. llms.txt lists this book for machines.

What this book is not

Not the contract. The exact CLI surface, JSON fields and manifest rules live in docs/cli.md. This book teaches the chain and points there.

Not the product site. The homepage shows the product; this is the long-form manual for people and agents who need to understand it.

Not a framework tutorial. The examples use Hello Worktree because it runs with Python 3 alone; the same chain applies to any stack.
