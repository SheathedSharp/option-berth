oberth keeps one answer per Git worktree: what should run, whether it really is running, and why not. A person reads a table; a coding agent reads the same command with --json. This book teaches the chain behind both.

Four checkouts, four guesses

Git worktrees solved parallel code, not parallel runtime. Four checkouts of one repository share a port range, a database name and a shell history, so every session re-derives the same three facts — and derives them slightly differently each time.

oberth writes those facts once, in one order, and lets every reader read the same thing: worktree → manifest → service → run → runtime facts. Nothing downstream re-invents what upstream already published.

One chain, five stations

The five stations of the chain of facts
StationThe question it settlesWhat it may not do
WorktreeWhich checkout does a run belong to?Belong to a checkout it did not start in.
ManifestWhat should run, on which port, after what?Be guessed from a running process, or adopted by a model.
ServiceWhich declaration starts, in which order, on which address?Start a dependent service before its dependency is ready.
Runpid, start, end, exit code, log path.Count as listening because the process exists.
Runtime factsAlive, listening, healthy, and why it ended.Turn a table it could not read into “not running”.

The chain of facts follows the five stations in order, one chapter section each.

The loop you actually run

Five commands cover a working day. Each replaces a shell one-liner that had to be re-invented per checkout.

How to read this book

  • First time here. Install oberth, then follow Your first worktree: one example project, five commands, from an empty checkout to a clean stop.
  • You already run things. Read the chain of facts and worktrees and runs, then use the command chapters as you need them.
  • You are wiring an agent. Start at Facts as JSON, then coding agents for the three moments to call oberth.

Two readers, one interface

There is no second interface, no MCP server and no model in the core. The CLI is the contract; --json is the same contract in a machine shape.

llms.txt lists this book for machines, and llms-full.txt carries every chapter as plain text.

What this book is not

Not the contract. The exact CLI surface, JSON fields and manifest rules live in docs/cli.md; this book teaches the chain and points there. Not the product site. The homepage shows the product. Not a framework tutorial. The examples use Hello Worktree because it runs on Python 3 alone; the same chain applies to any stack.
