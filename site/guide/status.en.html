status reads the worktree, its manifest and its runs, then returns the runtime facts as they are. It is the command a session opens with, and it is allowed to say that it cannot see.

Four facts, not one

The product keeps apart what a shell one-liner collapses. A live process, a bound port, a passing health check and an exit reason are four different facts, and none of them implies the next.

The four runtime facts
FactThe question it answersWhere it comes from
ProcessDid the process stay alive?The run record: pid, start, end, exit code.
ListenerWhich address is actually bound?The listener observation, with its own trust state.
HealthDoes the service answer its health check?The declared HTTP, TCP or command check.
ExitIf it ended, why?The most recent exit reason and the log it points at.

Read the table

The human table is ordered by project, then by service, dependencies, code and failure reason. Each service line carries both the declared port and the current runtime fact. The failure section shows the most recent exit only while it is still that service's current last_exit.

  • A portless worker is printed as no port. It is observed through its run record, not through a listener.
  • A port: auto service that has no port yet prints auto port unassigned. That is not a failure.
  • Only listeners the manifest did not declare are listed separately. A port that belongs to a service appears with that service.
  • code_changed_since_start means the process is running older code than the checkout, and it comes with a restart hint. It is a code fact, not a runtime failure.

For agents: --brief and --json

The top-level object from --json is worktree. --brief keeps only the runtime facts, which makes it the cheapest place to start; the full read adds the git summary, drafts, the change list and the manifest fields of each service.

  • worktree.identity is the wt_… value that down --identity uses and that appears in data paths.
  • worktree.services[] carries running, port_actual, health_status, pid and run_id.
  • exits[] carries the reason, the exit code and a hint that points at evidence which really exists.
  • observation appears only when the listener table cannot be trusted; when it is absent, the table was usable.

When observation fails

A sandbox, a permission wall or a platform change can break the listener scan. The engine then reports one of observation_empty, observation_unrecognized, observation_incomplete, observation_blind or observation_bind_denied. None of those codes means “nothing is listening”, and still less “not running”. The human table says listening unknown, and a port: auto candidate is verified by binding instead of by trusting an empty table.

Run this check in the same kind of process that failed. If the result is blind, retry from a normal terminal, or run oberth runtime service run --detach there and retry. Do not loop the same start inside the sandbox and read timeouts as failures.

What status never says

It is not a machine-wide port radar: it answers for this worktree's declared services, not for every socket on the host. It does not hand “why did it fail” to a model. A fixed reason code and a log are the answer. An unread fact is never written as a fact, so unknown is not success and an absent field is not zero.
