这本指南里的每条命令都在读写同一条链：worktree → 清单 → 服务 → 运行 → 运行事实。每个站点只有一个写入者，下一站只读上一站发布的东西。没有第二个状态来源。

Runtime World 的四元组

一个 checkout 的 Runtime World 是四个位置组成的记录。Intent、execution、observation 和 causal diagnosis 各自回答不同的问题，缺失的事实不会被旁边的位置补出来。

四个位置与各自的写入者
位置写入者发布什么
Intent确认清单的人oberth.yaml：服务、端口、depends_on、健康和 prepare。
Execution运行注册表一次运行的启动顺序、实际地址、退出码和日志路径。
Observation本轮的 OS 扫描进程、监听、健康和退出，四项独立事实。
Causal diagnosis诊断环节根因、被阻塞的服务，以及脱敏后的 first_error。

五个站点

四个位置由五个站点承载。多出来的是 worktree 本身，它在任何服务启动之前先确定归属。

每一站发布什么，下一站读什么

worktreeGit，由引擎观察checkout 根路径，以及一次运行所属的 wt_… 身份。

服务启动时的引擎启动的是哪条声明、按什么顺序、落在哪个地址上。
运行运行注册表一个进程的 pid、开始、结束、退出码与日志路径。
运行事实本轮的观察活着、在监听、健康，以及更早那次运行为什么结束。

顺序为什么重要

只给一个“它起来了吗”的布尔值，整条链就被压平了，每个读者都得自己把剩下的推一遍。所以每一步都先发布，下一步才被允许据此做决定：归属先于生命周期，生命周期先于观察，观察先于就绪。

所以 up --wait 返回的是真的答案，status 也能一边说服务在运行、一边说端口未知，而不自相矛盾。

因果诊断

诊断读取整条链。崩溃会沿 depends_on 传播，但报告只保留一个根因，把下游服务列为被阻塞，读者不会去追三个共享同一原因的症状。

同一轮诊断跨代比较启动时间、退出码和日志指纹。反复重启的服务会带着证据报成循环，不会因为当前 pid 活着就算健康。

一次运行属于启动它的 checkout

归属由三项共同确定：这一轮的路径观察、清单的内容索引和运行身份。所以同一个仓库的两个 worktree 不会串服务，也不会串端口、数据库名或停止动作。

端口遵守同一条规则。port: auto 按一次运行预留、停止时交还，第二个 checkout 问“那个 API 端口”时得到的是它自己的答案，不是一次冲突。端口被另一个 checkout 占用时，诊断报告持有者，不会建议杀掉别人的进程。

没读到的事实保持未知

失败、取消和不完整的扫描，都不能变成“空闲”“已消失”或“健康”。监听表里没有这个端口，只说明这条事实没被观察到，绝不代表端口空闲。信号发送成功，也只说明信号送到了，不代表进程已经退出。

没读到的事实写成未知，未知不是成功。status 让这条规则看得见，产品的边界把它变成一条产品边界。

每一站在哪一章

  • 声明该跑什么讲清单，以及模型不许对它做的那件事。
  • up讲依赖顺序、自动端口，以及就绪到底证明了什么。
  • 同时跑多个 worktree讲归属、数据路径和遗留 checkout。
  • logs讲运行自己的输出，不用重拼一条 shell 管道。
  • status讲四种运行事实，以及那句诚实的“我看不见”。
